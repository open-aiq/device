# Open AIQ firmware

Rust/ESP-IDF firmware for the ESP32-S3 Open AIQ monitor. It replaces the
earlier Arduino firmware for the ESP32 DOIT DevKit v1, which remains available
in git history. Over Bluetooth the monitor still goes by `AirMonitor-XXXX`.

It reads a PMS5003 and SHT30,
renders three screens on a 128x64 I2C OLED, provisions over a passkey-secured
Nordic UART BLE service, persists configuration in NVS, uploads ten-minute
averages and important log events, and installs owner-approved OTA updates.

## Wiring

[`src/board.rs`](src/board.rs) is the source of truth for GPIO selection and
hardware initialization: shared I2C at 400 kHz, PMS5003 UART at 9,600 baud,
and active-low buttons with internal pull-ups.

| Device | Signal | ESP32-S3 GPIO |
| --- | --- | --- |
| OLED + SHT30 | SDA | 5 |
| OLED + SHT30 | SCL | 4 |
| PMS5003 | sensor TX -> ESP RX | 17 |
| PMS5003 | sensor RX <- ESP TX | 18 |
| PMS5003 | SET: high runs, low sleeps | 8 |
| PMS5003 | RESET (pulled up on the board, not driven yet) | 16 |
| Button | Right, active-low | 15 |
| Button | Left, active-low | 6 |
| Button | Pair, active-low (not read yet) | 7 |
| Status LED | WS2812 data | 48 |

These match the Proto2 rev B carrier board. Older breadboard builds used SDA 8,
SCL 9, sensor TX 18, sensor RX 17, and buttons 4 (right) and 5 (left).

Power the OLED and SHT30 at 3.3 V and ensure the shared I2C bus has pull-ups.
The PMS5003 normally uses 5 V power; verify the module's UART logic levels.

At boot the firmware accepts an SHT30 at `0x44`/`0x45` and OLED at
`0x3C`/`0x3D`. Missing or ambiguous devices are logged without stopping other
services. Controller type cannot be inferred from its address.

## Sampling

We let the PMS5003 rest between short bursts, because its fan and laser wear
out with run time. The timing lives in
[`src/sensors/schedule.rs`](src/sensors/schedule.rs):

| Constant | Value | What it does |
| --- | --- | --- |
| `PMS_CYCLE_MS` | 5 min | One wake, warm-up, sample and sleep cycle; two per upload |
| `PMS_WARM_UP_MS` | 30 s | Frames are ignored while the fan settles (datasheet minimum) |
| `PMS_SAMPLE_MS` | 30 s | Every frame in this window is averaged, about 13 per burst |
| `CLIMATE_INTERVAL_MS` | 20 s | SHT30 reading and screen/BLE live refresh (`src/lib.rs`) |
| `UPLOAD_INTERVAL_MS` | 10 min | One averaged upload (`src/lib.rs`) |

The SHT30 is also read once right after boot, so the screen has temperature
and humidity within a second or so.

So the fan and laser run 60 s in every 5 minutes. Uploads only go out while
the sensor rests, so a burst is never split. While it rests, the screen keeps
the last burst's PM. If a burst brings no frames, PM shows as missing and a
`sensor` log event is recorded.

The manufacturer's manual is in [`docs/datasheets/`](docs/datasheets/), and
[The particle sensor](https://docs.air-iq.net/device/particle-sensor/) on the
docs site explains why we chose this timing, with sources.

## Screens

The buttons cycle three screens. Left goes back, right goes forward.

| Screen | Shows |
| --- | --- |
| AQI | The AQI as a large number, its band by name and on a six-step gauge, the feels-like temperature, and a WiFi icon (struck through when offline) |
| Readings | PM1.0, PM2.5 and PM10 in µg/m³, then temperature and humidity |
| Network | The WiFi name with signal bars, the IP address (or `Offline`), the last upload in words such as `Sent 2m ago` (or `Not set up yet`), and the firmware version |

The OLED has one colour, so the band shows as a name and a gauge: one box per
band, Good on the left, with the current one filled. The colour itself is on
the [status LED](#status-led). Band names and colours come from the shared
design tokens: `src/aqi/bands.g.rs` is generated by `make tokens:sync` in the
docs repository, so don't edit it by hand.

You'll see `Open AIQ` / `starting...` from power-on until WiFi has had its
first try, `warming up...` until the first particle burst lands, and
`Hold both btns: pair` on a monitor that isn't set up yet. The font is ASCII
only, so units read `ug/m3` and `C`.

Changing a layout? `make screens` prints every screen as ASCII art on your
computer, no hardware needed. The tests in [`src/display/mod.rs`](src/display/mod.rs)
fail if anything is drawn off the screen or over something else.

## Status LED

The RGB LED on GPIO 48 is a diagnostics light. It shows what the board is
doing when you can't see the serial log, or when the screen itself is the
problem. When all is well, its heartbeat also carries the AQI band's colour. It's the onboard LED on the ESP32-S3-DevKitC-1 v1.0 and D1 on the SMT
board. (DevKitC-1 v1.1 moved its LED to GPIO 38, so it stays dark there.)

It's kept dim on purpose, about 10% brightness. A background thread redraws it
about 30 times a second, so it keeps going during WiFi connects, uploads and
OTA downloads. The logic and its tests are in [`src/led/mod.rs`](src/led/mod.rs).

Only one pattern shows at a time. Higher rows win:

| Pattern | Meaning |
| --- | --- |
| White fade-in | Booting |
| Amber, slow breathing | Downloading or installing an update |
| Two green or two red flashes | Pairing worked, or didn't |
| Steady blue | A phone is connected (or the passkey is on screen) |
| Blue, slow breathing | Pairing window open, waiting for a phone |
| Red blinks, then a pause | A fault; count the blinks (below) |
| Yellow, 1 s on / 1 s off | Not provisioned yet |
| Dim white, slow breathing | PMS5003 warming up; frames don't count yet |
| Dim green, brighter tick per frame | PMS5003 sampling; each tick is a frame arriving |
| Dark, tiny blink every 5 s | PMS5003 resting; the firmware's alive and well. The blink is the AQI band's colour (below), or green before the first reading |

The heartbeat's colours follow the AQI bands. They're the shared band colours
with most of the white taken out, because pastels look nearly white on a dim
LED:

| AQI | Band | Heartbeat |
| --- | --- | --- |
| 0–50 | Good | Green |
| 51–100 | Moderate | Yellow |
| 101–150 | Slightly Unhealthy | Orange |
| 151–200 | Unhealthy | Red |
| 201–300 | Very Unhealthy | Purple |
| 301+ | Hazardous | Pink |

A red heartbeat is one short blink every 5 seconds. A fault is brighter,
longer blinks in a counted group, so the two don't look alike.

Fault codes. If there's more than one, you'll see the lowest:

| Blinks | Fault | Where to look |
| --- | --- | --- |
| 1 | PMS5003 silent: a whole burst with no frames, or reads failing | Its cable, 5 V power and the TX/RX pins |
| 2 | SHT30 missing, or its last read failed | I2C wiring and pull-ups |
| 3 | OLED not found at boot | The OLED's cable; reboot after fixing it |
| 4 | WiFi is set up but not connected | Router range, or the saved network |
| 5 | The backend didn't accept the last upload | The `upload failed http=` log line |
| 6 | A new update is running but not verified yet | Clears after the first good upload |

If the PMS5003 is sampling but the green never ticks, frames aren't arriving.
That usually points to its wiring, so you'll know before the burst ends and
code 1 appears.

## Build and quality gates

The default controller is SH1106:

```sh
OLED_CONTROLLER=sh1106 cargo build --release
OLED_CONTROLLER=ssd1306 cargo build --release
make format:fix
make verify HOST_TARGET=aarch64-apple-darwin
```

Use `HOST_TARGET=x86_64-unknown-linux-gnu` on Linux. `cargo fmt` rewrites source;
CI uses `cargo fmt -- --check`. Clippy uses `-D warnings`. Host tests cover the
portable library and separate ESP32-S3 jobs compile both OLED selections.

Flash only when hardware is attached:

```sh
make flash            # build, flash with partitions.csv + rollback bootloader, monitor
make board:info       # read-only: chip and flash size
```

### Partition table and OTA

[`partitions.csv`](partitions.csv) holds two 1.94 MB OTA app slots (`ota_0`,
`ota_1`) and fits any ESP32-S3 module with 4 MB of flash or more. `nvs` keeps its
default offset, so provisioning survives the switch. Moving from the old
single-app table needs **one USB flash** with `make flash`, which passes
`--partition-table partitions.csv` and the ESP-IDF bootloader built with
`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`. After that, updates arrive over the air.
Plain `espflash flash` without these flags substitutes espflash's own table and
bootloader.

`make image` writes the OTA image (`target/xtensa-esp32s3-espidf/release/device_rust.bin`)
and prints the size and SHA-256 that a firmware release is published with.

## Serial buttons

The `serial-buttons` cargo feature (on by default) lets the serial console stand
in for the physical buttons. With `make monitor` open, type a line and press Enter:

| Line | Same as |
| --- | --- |
| `BTN:PAIR` | Holding both buttons for 3 s (opens pairing mode) |
| `BTN:LEFT` / `BTN:RIGHT` | Left / right button |
| `BTN:HELP` | Prints the list |

Both the UART0 console and the native USB-Serial-JTAG port are read. Build with
`--no-default-features` to remove the feature.

## Provisioning over BLE

The device is `AirMonitor-XXXX` (last two MAC bytes) and exposes the Nordic UART
Service:

| UUID | Role |
| --- | --- |
| `6E400001-B5A3-F393-E0A9-E50E24DCCA9E` | Service |
| `6E400002-B5A3-F393-E0A9-E50E24DCCA9E` | RX: phone writes commands |
| `6E400003-B5A3-F393-E0A9-E50E24DCCA9E` | TX: device notifies replies |

### Pairing mode and security

BLE is **off by default**. Hold both buttons for 3 seconds (or type `BTN:PAIR`)
to start advertising for 5 minutes. The OLED shows `PAIRING` and a countdown.

- **Authenticated pairing.** RX and TX require an encrypted, MITM-authenticated
  link: LE Secure Connections with passkey entry, using IO capability
  `DisplayOnly`.
- **Passkey.** Each pairing window gets a fresh random 6-digit passkey. When a
  phone starts pairing, the passkey is shown on the OLED and printed to the
  serial log as `BLE PAIRING PASSKEY: 123 456`. It is never uploaded.
- **Bonds.** Bonds persist in NVS (at most 3), so a paired phone reconnects
  without a passkey. It still needs pairing mode to find the device.
- **Window.** While a phone is connected, the window stays open until 10
  minutes without commands. After a disconnect, advertising continues for 60
  seconds so bonding reconnects succeed, then BLE stops.
- **Factory reset.** `CLEAR` wipes provisioning and all bonds.

The earlier Arduino firmware has no pairing security. The Open AIQ
app requires this firmware.

### Commands

Commands are newline-terminated text. Replies are newline-terminated lines sent
as notifications of up to `MTU - 3` bytes (MTU 247 is requested; 20-byte chunks
at the default MTU). Clients must reassemble notifications until `\n`. Receive
lines are limited to 512 bytes. Secrets are never echoed.

| Command | Reply |
| --- | --- |
| `PING` | `PONG` |
| `STATUS` | `WiFi: connected IP: <ip>` |
| `INFO` | `INFO_BEGIN`, `FW:<ver>`, `MAC:<hex>`, `DEVID:<id>`, `DEVKEY_SET:0/1`, `WIFI:connected/disconnected`, `SSID:<ssid>`, `IP:<ip>`, `LAST_UPLOAD:<http>,<secs ago>` or `LAST_UPLOAD:none`, `INFO_END` |
| `SCAN` | `SCAN_BEGIN`, `NET:<rssi>,<open/secured>,<ssid>` (strongest first, at most 15; SSID may contain commas), `SCAN_END`; `ERROR:SCAN` on failure |
| `SSID:<name>` / `PASS:<secret>` | `OK: SSID set to <name>` / `OK: password set` |
| `LAT:<deg>` / `LON:<deg>` | `OK: LAT set to <6dp>` / `OK: LON set to <6dp>` |
| `DEVID:<dev_...>` / `DEVKEY:<sk_...>` | `OK: DEVID set to <id>` / `OK: device key set` |
| `SAVE` | `SAVE_BEGIN`, `WIFI_CONNECTING`, then `SAVE_OK` + `IP:<ip>`, or `SAVE_FAILED:WIFI` / `SAVE_FAILED:STORAGE`, then `SAVE_END` |
| `LOAD` | `LOAD_BEGIN`, `SSID:`, `PASS_SET:0/1`, `LAT:`, `LON:`, `DEVID:`, `DEVKEY_SET:0/1`, `LOAD_END` |
| `READ` | `READING:{json}` with the latest 20 s sample (PM from the latest burst), or `ERROR:NO_READING` |
| `LIVE:ON` / `LIVE:OFF` | `OK: live on/off`; while on, `READING:{json}` after every sample until disconnect |
| `OTA:CHECK` | `OK: ota check`; the device checks for an approved update right away (`OTA:NONE`, `OTA:STARTING <ver>`, `OTA:FAILED`) |
| `CLEAR` | `CLEARED all stored config` (also removes BLE bonds) |

`READING` JSON uses the upload payload's keys:
`{"pm1_0":3,"pm2_5":12,"pm10_0":18,"aqi":57,"temperature":24.5,"humidity":40.0,"heat_index":24.9,"uptime_ms":123456}`.
Fields are `null` while a sensor is missing.

Setters change RAM only; `SAVE` persists them and reconnects WiFi. Credentials
are written to NVS even when `SAVE_FAILED:WIFI` is returned.

## Backend communication

All device requests send `X-Device-ID`, `X-Device-Key` and
`X-Firmware-Version` (`CARGO_PKG_VERSION`) to `BACKEND_BASE_URL`.

| Request | When |
| --- | --- |
| `POST /data` | Every 10 minutes with the averaged reading (first upload after the first burst, about a minute after boot) |
| `POST /device/logs` | After each successful upload and once WiFi is up after boot |
| `GET /device/ota` | After each successful upload, or on `OTA:CHECK` |
| `POST /device/ota/status` | During an update: `downloading` (every 10 %), `installing`, `succeeded`, `failed` |

### Device logs

WARN and ERROR records, plus important events logged with `event!("tag", ...)`,
are kept in a 64-entry RAM ring buffer. Events include boot with reset reason,
WiFi, upload failures, BLE pairing, provisioning and every OTA step. They are
uploaded in batches of at most 50:

```json
{"entries":[{"level":"warn","tag":"wifi","message":"reconnect failed: ...","uptime_ms":183000,"boot_count":12,"ts":1793700000}],"dropped":0}
```

`ts` is SNTP Unix time and is omitted until the clock syncs. `boot_count` is
stored in NVS namespace `sys`, so `CLEAR` does not reset it. Never log secrets:
log entries are uploaded.

### OTA updates

1. The owner approves an update in the mobile app.
2. `GET /device/ota` returns
   `{"data":{"job_id","version","url","sha256","size","status"}}`, or
   `{"data":null}` when nothing is approved.
3. The device streams the image over HTTPS into the inactive slot, checking size
   and SHA-256. It reports `downloading` progress, activates the slot, reports
   `installing` and reboots. If the first `downloading` report returns 409, the
   job was cancelled and the device skips the update.
4. The new image stays pending-verify until its first successful upload. It
   then marks itself valid and reports `succeeded`. If it is not verified within
   5 minutes, or crashes, the bootloader rolls back. The old image then reports
   `failed: rolled back to <ver>`.

The OLED shows the progress as `NN%` over `Updating, keep power` during the
download; BLE and sampling pause.

An empty NVS can be seeded in a development build without committing secrets:

```sh
MOCK_WIFI_SSID=... MOCK_WIFI_PASSWORD=... \
MOCK_DEVICE_ID=dev_... MOCK_DEVICE_KEY=sk_... \
MOCK_LAT=24.8607 MOCK_LON=67.0011 cargo build
```

Set `WIPE_CONFIG_ON_BOOT=1` only for a deliberate reset build. Mock values are
compiled into that binary and must not be distributed. `BACKEND_BASE_URL`
defaults to `https://api.air-iq.net/api/v1`. HTTPS uses ESP-IDF's embedded CA
bundle.

## Manual hardware acceptance

For each OLED controller build:

1. Confirm the expected OLED and SHT30 addresses in the boot log.
2. Confirm temperature and humidity samples every 20 seconds, and that the
   PMS5003 logs `awake, warming up` every 5 minutes, then `asleep after N
   frames` 60 seconds later (N is about 13) with the fan audibly stopping.
3. Confirm `Open AIQ` shows from power-on, and that buttons (or `BTN:LEFT` /
   `BTN:RIGHT`) cycle the AQI, readings, and network screens without bounce.
   Check the WiFi icon is struck through with the router off, and that the
   resting heartbeat matches the AQI band's colour.
4. Confirm BLE is not advertising until `BTN:PAIR` / both-button hold. Confirm
   writes before passkey pairing are rejected, and that the passkey shown on
   the OLED or serial log pairs.
5. Exercise `PING`, fragmented commands, `INFO`, `SCAN`, `LIVE:ON`, `LOAD`,
   `SAVE`, and `CLEAR` (bonds removed) over BLE.
6. Verify bad WiFi credentials leave BLE available, then provision valid ones.
7. Verify an authenticated upload returns HTTP 201 and survives a reboot.
8. Disconnect each sensor in turn and verify other services keep running.
9. Publish a newer release, approve it in the app and verify `succeeded`.
   Verify that a wrong `sha256` is rejected without switching slots, and that a
   panicking image rolls back and reports `failed`.
